IOCP(Input/Output Completion Port)란 무엇인가? 
윈도우 운영체제에서 제공하는 비동기 I/O 완료 통보 메커니즘

기존 방식 (Select, Worker Thread): 클라이언트가 1,000명이면 스레드도 1,000개를 만들거나, 루프를 돌며 "데이터 왔니?"라고 계속 물어봐야 합니다(오버헤드 발생).

IOCP 방식: I/O 작업(데이터 받기/보내기)을 운영체제에 맡겨두고, 작업이 **완료(Completion)**되었을 때만 OS가 미리 준비된 **스레드 풀(Worker Threads)**에 신호를 줍니다.

IOCP 핵심구조

Completion Port (CP): 커널에 생성되는 큐(Queue)입니다. 완료된 I/O 정보가 여기에 쌓입니다.

Worker Threads: CP를 감시하다가 완료 신호가 오면 꺼내서 처리하는 일꾼들입니다. 보통 CPU 코어 수 * 2만큼 생성합니다.

Overlapped I/O: 비동기 작업을 위해 데이터를 실어 보낼 구조체입니다.

Accept Thread: 새로운 클라이언트의 연결만 전문적으로 받는 스레드입니다.

1. 에러 원인 분석: RecvBuffer의 커서 관리 문제
콜스택 : Session::Receive() -> RecvBuffer::WritePos() -> _buffer[index]
여기서 _writePos가 _buffer의 실제 크기(_capacity)와 같거나 커졌기 때문에 벡터 범위 초과 에러가 발생합니다
원인
데이터 누적: Session::OnRecv 루프 내에서 패킷을 처리한 후 _recvBuffer.OnRead(header->size)를 호출하여 _readPos를 뒤로 밀지만, 정작 데이터를 쓰는 위치인 _writePos는 계속 뒤로만 이동합니다
Clean 타이밍 문제: 현재 Session::OnRecv 마지막에 _recvBuffer.Clean()을 호출하고 있지만, 만약 패킷이 아주 작게 쪼개져서 오거나 버퍼의 남은 공간(FreeSize)이 다음 수신을 받기에 부족한 상태가 되면, _writePos가 벡터의 끝에 도달하게 됩니다.
Receive() 예약 시 검증 부족: Session::Receive() 함수는 호출될 때마다 _recvBuffer.WritePos()를 통해 다음 쓰기 위치를 가져오는데, 이때 _writePos가 이미 _capacity에 도달해 있다면 즉시 에러가 발생합니다.
